# Runtime resource registry context

[Current task](resource-registry-retention.md)

## 2026-11-24 — Dependency update review

[accepted] An isolated probe used Fyrox 1.0.1, the game's `LoaderOwnedIo` and a registered WAV loader. After requesting 128 distinct missing WAVs, awaiting their errors and advancing the cache past 60 seconds, the manager contained zero resource objects and the registry still contained 128 UUID/path pairs. `ResourceRegistry::path_to_uuid` iterates over the map. Repeated visits to a fixed set of paths reuse entries.

`ResourceManagerState::update` owns expiry and only publishes the removed path. Its event broadcaster also sends strong handles on addition and successful load. A subscriber that keeps these events until a later tick extends resource lifetimes. A delayed removal by path could erase the mapping of a resource requested again in the meantime.

[open] Compare cleaning up under the manager lock at eviction with reconciling live entries after eviction. Account for header locks and allocations on the simulation thread. Establish whether callers may ever store a bare UUID across expiry. Preserve sharing while a handle is alive and keep registry writes off disk.

## 2026-11-24 — Resource identity and eviction

Source comparison at `e8c565a` on Linux x86_64, using the Cargo sources for 0.36.2 and 1.0.1. In 0.36.2, `ResourceManagerState::request` creates `ResourceKind::External(path)`. Its private list of timed handles supplies the path lookup. In both versions, `update(dt)` resets the TTL to 60 seconds while another strong handle exists, counts down when the manager is the sole owner and removes the entry at expiry. The loading task itself holds a handle. An actor, a preparation dependency or the engine's session pin also counts. A separately cloned descriptor can outlive its cached handle.

In 1.0.1, a managed external handle identifies the asset by UUID. A path hit checks the cached handles via the registry. On a miss, `find_uuid_or_register_new` scans the UUID-to-path B-tree for the path and, for a supported extension, registers a random UUID before starting I/O. The loading task looks the path up by UUID. An error opening or decoding a file therefore also leaves a registered path. Eviction removes the timed entry and uses the registry to report its path. It leaves the mapping available to resolve that UUID later. Project loaders own file I/O, the registry starts empty and loaded, and `LoaderOwnedIo::can_write() == false` skips even serialization in `ResourceRegistry::save_sync`. See the [upgrade history](../dependency-and-build-cleanup/).

[proposed] The stable key for requesting a map or sound is its logical path. All current production callers request by key and retain handles or prepared data. The bare UUID construction in the resource tests checks the unloaded state. No gameplay, map or network consumer was found that resolves a saved runtime asset UUID. An old UUID may expire with the timed entry. The next request for that path may create a new UUID. A future saved-game or editor contract requiring stable UUIDs across unloads would need a separately owned asset catalog. Keep `Session` promotion, including on a cache hit. It holds one strong handle per pinned asset until system shutdown and applies to failures too. `WhileUsed` adds no engine pin.

[proposed] Start with the public 1.0.1 API. Within one manager state guard, record `len()`, call `update(dt)`, and compare lengths. This update only retains or removes entries. With no eviction and no deferred cleanup, the comparison adds constant work. After an eviction, borrow `state.iter()`, collect the surviving UUIDs, collect the registry-only UUIDs from `registry.inner().keys()`, and remove those with one mutable registry guard via `unregister(uuid)`. Keep the manager state guard through removal so a worker requesting the same path observes one coherent cache and registry. Collect live UUIDs before taking the registry guard. This relies on the engine's private, exclusively runtime-populated registry. Pinning and world preparation continue to use the ordinary request path.

The reconciliation costs a pass over the surviving handles and registry, plus B-tree removals. Reuse a UUID set and a removal vector across cleanup passes. Reading a survivor's UUID takes its resource-header lock. For the tick path, use a nonblocking attempt and defer the pass if a header is busy. Never delete on a partial snapshot. Remember to retry even if the next update evicts nothing. Sustained contention can delay cleanup, so measure retry behavior and tick cost under churn during implementation. An opt-in cleanup inside Fyrox's expiry branch can instead unregister exactly the UUID already read there, without inspecting survivors. This would require maintaining a dependency change until supported upstream. It is the alternative if tick cost or deferred cleanup proves material. Event subscription queues strong handles and delayed removal by path can race with a new request. Replacing the manager or dropping session pins does not address this mismatch at its owner.

An isolated Rust probe linked the locked 1.0.1 libraries, copied the game's `LoaderOwnedIo`, and registered a WAV loader using the real Fyrox decoder. It requested 32 distinct valid WAV paths and 32 missing paths and awaited each outcome. One successful handle was kept as a session-pin equivalent. After the loader handles drained, one `update(61.0)` left one cached object and 64 mappings. Reconciliation under the same state guard left one of each. A worker started a request for a previously failed path during maintenance. Following release, two requests for that path shared the same new handle and UUID, distinct from the expired UUID. Requesting the pinned path returned its original handle. This probe exercised the public operations and ownership rule outside the game. It did not measure timing, exercise contended header reads or run a headless world. Production implementation and the task's regression checks await design approval.

## 2026-11-24 — Retaining or downgrading the Fyrox crates

The author asked whether 0.36.2 better fits the current WAV-by-path workflow. Both versions already provide the shared pending handle, typed result and unused-resource TTL that gameplay uses. The 1.0 registry lets saved asset references survive moves. A Rust string literal naming a WAV still needs editing after a rename. Slice can keep shipping WAVs through its generated embedded catalog and registering logical paths in memory without generating or checking in any `.metadata` files. The stock editor/project workflow and its rationale are described in the [Fyrox release notes](https://fyrox.rs/blog/post/fyrox-game-engine-1-0-0-rc-1/#resource-management).

The locked Cargo graph and the sound crate's `SoundBufferResource = Resource<SoundBuffer>` tie the client audio API directly to `fyrox-resource` 1.0.1. An additional 0.36.2 resource crate introduces incompatible handles and resource traits. A coordinated downgrade is viable. In an isolated copy of `e8c565a`, restoring the previous resource adapter, affected tests and sound API call, pinning the three Fyrox crates to 0.36.2 across the workspace and resolving their dependencies produced a working Linux `cargo check --offline --workspace --bins --tests --locked` with wgpu 30.0.2. This was a compilation check. Future UI 1.0.1 also takes 1.0 texture/resource types. UI is still outside the game build. The [completed Vulkan UI experiment](../fyrox-ui-gpu-textures/) is specific to its tested versions.

An isolated comparison used both versions of the actual `SoundBuffer::raw_generic(DataSource::from_memory(...))` entry point on all 29 WAVs under `src/assets/sounds`. Channel count, sample rate and sample count matched for every file. The largest absolute sample difference was 0.00003052. For timings on Linux x86_64, the probe loaded the input bytes before timing and decoded each asset sequentially with the corresponding release libraries, alternating version order between passes. After one warm-up pass, the seven-pass median for the sum of decoder calls was 272.6 ms on 0.36.2 and 61.5 ms on 1.0.1. This comparison excludes I/O, game startup scheduling, audio playback and caching. The new sound crate uses Symphonia. The old generic buffer constructor also cloned a `Cursor<Vec<u8>>` for error recovery on this path. For `rotating_around_w.wav` that clone copied 15,495,886 input bytes. The newer constructor omits that clone. These are sound-stack results, and do not establish any performance improvement in the resource manager itself.

[proposed] Keep the 1.0.1 family together, retain the current path-based authoring workflow and address runtime registry growth locally. A coordinated 0.36.2 rollback removes the UUID registry but also gives up the measured audio improvement and requires revalidating the planned UI integration or isolating two type families. No version change has been approved.

## 2026-11-24 — Author decision and manual cleanup

[accepted] The author considers the observed registry behavior acceptable for present sessions. Repeated visits to a fixed set of maps and sounds do not accumulate records. No current workload establishes a need for scheduled cleanup. The author requested a commented helper on `Engine` for possible future use, and approved closing the task after implementing it.

[superseded] The earlier proposal to reconcile after cache evictions would add work to the simulation tick. The accepted scope is a manual helper with no production call sites, timer or retry state. Session pins and ordinary Fyrox expiry retain their current behavior.

[accepted] `Engine::prune_resource_registry()` delegates to the private resource system. Its manager registers one runtime path per cached handle. Under one manager state guard, equal counts therefore allow an immediate return. Otherwise the helper copies registered UUIDs, subtracts all cached UUIDs (including pending, failed, pinned and still within TTL), and unregisters the remainder by UUID. It releases the registry lock while inspecting resource headers. The manager guard serializes the operation with path requests and eviction. Temporary storage exists only during manual maintenance. The headless map round-trip regression calls the engine helper twice, retains the pinned descriptor and verifies that re-requesting the removed external map assigns a fresh UUID.

Verification on Linux x86_64 in the uncommitted tree based on `e8c565a`. The locked release workspace build and Windows GNU workspace bins check passed without compiler warnings. Each of the three client test binaries passed 29 tests, including the updated map round trip and the resource tests. The sandbox denied socket creation in nine transport tests per client binary and 24 Matchbox tests. With isolated loopback connection settings, the release headless client reached `engine: ready` and ran until the ten-second smoke-test timeout. The graphical client could not open the X display. The sandbox also denied gamepad hotplug monitoring. No production server was contacted.
