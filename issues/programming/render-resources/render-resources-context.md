# Scanner ownership and data flow

[Current task](render-resources.md)

## 2026-11-24 — First caller and boundaries

The existing scanner and minimap take different paths. The HUD scanner draws directly into the window. Its bind group combines a rectangle transform, scanner orientation and six buffers borrowed from the presented world. Separately, two obstacle-course shader branches in `world_descriptor.rs` build an XWZ minimap pipeline, sometimes with generated map geometry. `WorldGpu::encode` draws this minimap into the scene output. Moving the minimap requires preserving its map-specific inputs and appearance. The [map compatibility task](../maps-out-of-sync-with-parser/) records why an existing obstacle-course map may be unsuitable as a test fixture.

[proposed] At activation the player requests a scanner for its own rendered world, keeps the instance and passes its output to an image widget. The effect registers its WGSL, binding layout and pipeline recipe. Prepare expensive pipelines off the tick and render hot paths and share compatible compiled pipelines. Each scanner owns its changing inputs and target. Bind the world's shared scene inputs once per applicable generation. A tick updates orientation and other scanner-specific values. The render thread consumes the latest complete update for that instance when its world is due. Resource creation, rebinding and removal have ordered delivery. A new scanner input must not allocate an unbounded queue of obsolete frames. Existing world uploads have a separate [coherence limitation](../gpu-data-grouping/).

[proposed] Keep the existing resource loader for reusable file-backed inputs. Track runtime targets by live instance and generation. Consumers can retain an image reference while their binding tracks target recreation. Dropping the producer stops scheduling it even if a widget still holds that reference. Agree on placeholder/last-image behavior and stale-handle protection. Prepared spare actors must not register visible passes. Headless activation skips graphics allocation and leaves gameplay data available.

[open] The first shared texture lookup is now needed by the scanner widget. Prove it here for dynamic targets before deciding how much of it a world output and the later [4D screen](../in-world-4d-screens/) can reuse. Verify that a second effect can supply different bindings and inputs without adding a scanner-specific branch to the scheduler or UI backend.

## 2026-11-25 — Two projections and a map-dependent effect

On dev at `d97ac5e`, the four red/blue scanner elements have two orientations. The fragment entry point reads world data only from `dynamic_data` (camera, player projections, radius and intensities). It also reads `scanner_data.orientation` and the widget's opacity. Five additional world buffers in the existing eight-entry bind group are unused by this fragment. [proposed] Draw one local image per orientation. Keep the rect and opacity on the displaying widget. Write straight-alpha RGBA to the target with replacement and blend once in the image pass. Keep the accumulation and color range under visual review at the partially transparent edges.

The obstacle-course XWZ minimap exercises different bindings, aspect and map-specific generated code. Both obstacle shader branches use the same minimap source. `WorldPreparation::finish` currently consumes `allowed_dyn_objects` together with the parsed map. Moving the compiler call to an actor would lose a generation input. [proposed] Retain the small map-specific generation settings with the shared map geometry as inputs to the effect's loading job. Share the generated pipeline across instances of that prepared map. Let the obstacle-course HUD owner opt in at activation. Compare the image at its current position before bloom, including radius on/off, at two scene scales using a compatible local fixture. Further design and lifecycle in the [per-world scheduling task](../world-render-passes/), context for 2026-11-25.

## 2026-11-25 — Common pipeline creation and per-world buffer ownership

[accepted] Keep a closed set of embedded WGSL programs and select the needed variant in Rust. The map resource still goes through the existing loader. Its main scene pipeline can be prepared as part of loading. A HUD minimap is an optional dynamic-texture request by its user. The pairing of main and minimap in the obstacle branches was a development shortcut.

[accepted] Keep the reusable CPU representation for generating BSP shaders with the loaded map geometry. Today each call to `generate_raymarch_shader_with_static_bsp_tree` builds a fresh tree, even when the next call uses the same geometry for a different WGSL template. The generator also reads static shape data directly for intersection code and takes the allowed dynamic object table. Retain the inputs these paths need, share them among shader preparations for this map, and keep dynamic per-instance uploads with the world. The author deferred the invalidation question.

[proposed] Put the simulation-side `WorldRenderSystem`, its render data and per-instance buffers under `engine/world/render`. The existing placement exception documents the coupling of this code to `WorldGpu` and slot internals. Replace that coupling with the scheduler's registration and publication operations. Keep frame encoding, slot storage and presentation inside shared rendering. Update the module comment, AGENTS placement note and architecture reference when the move lands.

[proposed] Use one shared `render/pipelines` module with built-in variant selection. Preparation takes the template, any map specialization, the device and target format. This work can happen before any world buffer exists. Bind an instance separately using its world buffers, any private inputs, sampled views and shared resources such as the skybox sampler. Store compatible compiled pipelines per device/map variant. Compile on a loading worker and propagate errors to the request. On a live replacement, retain the active pass until the replacement is ready. Limit replacements to the same input contract: `DynamicRenderData::update_dynamic_shapes_buffers_and_get_metadata` includes static negative spheres in the upload only for the non-generated variant. Changing that mode also requires a coordinated change to the CPU data and its consumers.

[proposed] Use one actor call `create_texture(effect, size)` returning a producer with `image()`. The closed effect enum carries named inputs. For `Scanner { plane }` the factory builds the fixed orientation uniform once. The live world data comes from the scene uniform. When an effect genuinely needs actor-written parameters, give its variant a typed input, for example a writable `Uniform<Params>` supplied by the actor's module and bound by the factory. That module can keep the writer and producer together. This supports several named inputs and prevents a caller from depending on buffer order. There is no per-effect trait requirement or public vector of raw buffers. Refer to the local image key from a same-world screen when the later [screen task](../in-world-4d-screens/) has a consumer.

On this revision, surface loss recreates the surface with the original adapter/device, and device loss ends the session with an error. Borrow the shared GPU context for creation or retain the necessary device/queue handles for a pending job. No live-device rebinding protocol is needed for this lifecycle.

## 2026-11-25 — Pipeline resources and instance readiness

[accepted] The author wants the Resource System to own asynchronous requests for compiled pipelines, with the same inspection, waiting and retention semantics as sound and world resources. [superseded] The earlier proposal to keep a separate device pipeline cache assumed only file-backed inputs belonged to the loader. Compilation itself is the expensive reusable result even with embedded WGSL. Keep the compiler and binding layouts in shared rendering and call the compiler from the resource loader.

### Map and pipeline dependencies

[proposed] Introduce one internal CPU map resource, `MapData`, keyed by the existing normalized map name. Its loader owns the existing disk-first resolution and single JSON parse. It holds geometry, materials, actor descriptions/defaults, scene selection, sky description and permitted dynamic shape kinds. Retain the derived CPU inputs for generated shaders with that map and initialize them once when graphics needs them. Headless loads the simulation data alone. The public `WorldResource` consumes this resource, prepares independent spare actors with the existing dependency collector, and in graphical mode awaits its required scene pipeline and sky. The descriptor retains the shared data and required resources. Actor constructors and activation keep their existing lifecycle.

A map-specialized pipeline can request the same `MapData` directly. Depending on the finished `WorldResource` from its own scene pipeline would make both wait on each other. `MapData` must be publishable without requesting actors' assets or any GPU resource. A built-in scanner pipeline needs only the published device. Hold Fyrox data guards only to extract an owned handle before awaiting or spawning work.

[proposed] Represent a pipeline request by its built-in variant, compile-time specialization and compatible target state. Include the normalized map key for geometry-dependent code. Keep scanner plane, target size, sky image and instance buffers out of the key. The manager already deduplicates a pending request by logical path and dispatches by extension. Use one internal, unambiguous encoding of the typed request into a virtual manager path (preserve map directories and aliases), with a loader that rebuilds the recipe from it. It does no shader-file I/O. Use the ordinary retention and dependency collector. A loader waits for device publication and runs generation and driver compilation on a blocking worker. Required startup failures reach the map waiter. BSP cache invalidation remains deferred.

### Dynamic texture producer

[proposed] The actor calls `world.render.create_dynamic_texture(&mut shared.resources, effect, size)` during activation. The world already knows the map and device. This convenience operation requests the pipeline from the supplied loader, then passes the possibly pending handle to the internal instance builder. Explicit preloading or map preparation may request the same pipeline earlier. Keep the public asset request for these callers. The instance is unique per call, and the actor gets an owning handle and a usable local image key immediately.

The handle exposes a nonblocking readiness check and an awaitable completion with the same terminal result. A background job awaits the pipeline, creates and validates the target and private bindings from owned inputs, completes the instance's readiness signal and reports the prepared pass to the world. `Ready` means the instance is prepared for publication. The world incorporates the completion during its next structural publication. Consumers see a placeholder through the first scheduled draw. Thus awaiting preparation can finish while the world is paused or before it ticks again. Propagate load/bind errors to waiters. On owner or world teardown, resolve pending waiters with cancellation and reject late completions by live world/instance ID. A cancelled instance releases its claims without cancelling a shared pipeline needed by another world. Blocking waits belong only to loading/test contexts whose awaited work progresses independently; avoid holding the device-publication thread, a resource guard or the world callback open. No polling of ready instances in the frame loop.

### Typed uploads and shader semantics

[accepted] Use the same typed uniform interface for the world's uniform buffers and actor-owned effect inputs. [proposed] Start with a thin `Uniform<T>` over a GPU buffer with a type marker. Allocate from the known host layout; write a borrowed `&T` through the owner's queue; lend a typed handle for instance binding. Existing fixed arrays can use `Uniform<[Shape; 256]>` and `Uniform<[PlayerForm; 16]>` and borrow their boxed arrays directly. The CPU render data keeps its working vectors. A write introduces no extra CPU mirror, lock, heap buffer or submission. Use GPU-layout types with checked sizes, field offsets and array strides. `Pod` alone only establishes that Rust bytes may be copied. Texture views, samplers and vertex/index buffers keep their own wgpu usages. Fixed-capacity collection and coherent multi-buffer updates remain in [overflow](../gpu-buffer-overflow/) and [upload grouping](../gpu-data-grouping/).

On dev at `d97ac5e`, `AllowedDynamicObjectsInBspTreeTable` selects which dynamic shape branches are emitted into generated WGSL. Separately, the CPU collector at `dynamic_render_data.rs` includes visible *static* negative spheres in the negative-shape array only for non-generated raymarch. Matching byte layouts or passing the dynamic-kind table alone cannot express that distinction. [proposed] Derive the collector's existing static-negative-sphere choice from the active scene recipe once and pass it to render-data collection; keep the generated minimap on the same geometry convention. Support a runtime replacement using compatible inputs. Before publishing a replacement with a different convention, all consumers need matching initialized buffers and metadata at the handoff. Keep the current plan on failure. A general switch between incompatible collectors is a separate design choice.

### Per-world sky

[accepted] The map selects the skybox and its sampler. Bind them in each consuming instance. [proposed] Support one path to a cubemap descriptor listing six named face image paths in +X, -X, +Y, -Y, +Z, -Z order. Resolve face paths relative to the descriptor; embedded defaults and external assets use the same decode/upload path. Async reads and blocking decode feed a six-layer sRGB GPU texture with a cube view. Validate all faces are square and the same size and report the offending path before upload. Today `load_cube_texture` in `gpu_context.rs` uses the last decoded face's dimensions for every layer.

Cache the cube by asset path. The world descriptor supplies sampling settings, defaulting to today's clamp/linear behavior. A sampler with identical settings can be reused while each world retains its own choice and bindings. A missing sky field in an existing map selects the shipped star sky. An explicitly broken selection is a named map dependency error. A different sky with the same pipeline changes only its bindings. The first path loader only needs the cube format used by this caller. Full material import and arbitrary shader-path loading have separate requirements.

## 2026-11-25 — Supported levels and implemented resource ownership

[accepted] Only `capture_the_flag_map` remains active. Move the other 24 level files into the existing archive, preserving their subdirectories. Remove the old non-BSP collector branch. CTF has a baked static negative sphere and the Hole actor supplies live negative spheres separately. The allowed dynamic table selects WGSL branches. Existing positive-shape uploads also supply material lookup. [superseded] The proposed collector switch and an urgent compatibility task were predicated on supporting the archived maps.

[accepted] The CPU asset is `LevelResource` containing `LevelData`. The descriptor and active renderer retain the level dependency. Derived render data and the BSP are initialized on demand and reused for the minimap. `RenderPipelineResource` and `CubemapTexture` are device assets. Live worlds own their own bind groups, buffers, sky selection and image instances. Scanner planes are fixed at construction and share the world dynamic uniform. Dropping the producer releases its registration on the next structural publication. Readiness covers preparation and validation. No first-draw acknowledgement crosses threads.
